## 1. GOALS AND SCOPE

**Goal:** From an Obsidian note (`.md`), automatically produce an explainer video about a scientific/engineering principle in the language requested for that video (first target: Vietnamese; 1080p, with voice-over and subtitles), running entirely on the local machine, with no internet needed during operation.

**In scope:**
- Generate a script from the note with a local LLM, with a human review step.
- Voice-over with a local TTS in the video's language (any language for which a local voice exists).
- B-roll: engineering/math animations with Manim, code generated by the LLM.
- A-roll: a talking 3D avatar, lip-synced with Rhubarb + Blender.
- Automated post-production with FFmpeg: scene concatenation, voice-over, loudness normalisation, subtitles.

**Out of scope:**
- Diffusion / text-to-video models (too heavy for an iGPU, physical motion is unreliable).
- Manual timeline editing. If manual tweaks are needed, open the `segments/` folder in any editor.
- Claude Code is **not** part of the operating pipeline (see §13).

## 2. DESIGN PRINCIPLES

1. **Every service and tool of the pipeline runs in a Podman container.** The host only needs `podman`, `systemd --user` and `bash`. The one deliberate exception: the graphical Blender used to *build the rig by hand* (§8.4); it is not part of the automated pipeline.
2. **Two kinds of container:**
   - *Long-running service* (LocalAI): managed with Quadlet (`systemd --user`), started on demand.
   - *Job* (plan, tts, render, assemble, …): `podman run --rm`, removed when finished.
3. **LocalAI is only an inference service. Orchestration is decided by the orchestrator.** LocalAI knows nothing about the pipeline steps; the orchestrator (Python, running in the `producer` container) decides step order, when to load/release models, retries and stops. The LLM is called in only two places: script generation and Manim code generation/repair.
4. **There is a human approval gate.** The LLM may misinterpret the source note; the voice-over step refuses to run until the script is approved.
5. **Per-scene synchronisation.** Each scene has its own audio file; the visual duration of the scene is forced to equal the audio duration. A single long voice file is never laid over the whole video.
6. **Run sequentially in groups.** The LLM group finishes → models are released from the GPU → only then 3D rendering runs (§5, §9).
7. **LLM-generated code always runs isolated:** a `--network=none` container that mounts only that scene's working directory.

## 5. PROCESSING FLOW

Each step reads/writes files in `projects/<slug>/`, so any step can be re-run on its own.

| # | Step | Container | Input | Output | Needs LocalAI |
| :-: | :--- | :--- | :--- | :--- | :-: |
| 1 | `plan` | producer | Note `.md` in the vault | `script.json` | ✅ role `llm` |
| 2 | **Review** | *(human)* | `script.json` | `script.json` with `"approved": true` | |
| 3 | `tts` | producer | Approved `script.json` | `audio/<id>.wav`, `timing.json` | ✅ role `tts-<lang>` |
| 4 | `broll` | producer (gen) + producer `--network none` (render) | Scenes with `type: broll` + `timing.json` | `broll/<id>.py`, `broll/<id>.mp4` | ✅ role `llm` |
| — | *Release all LocalAI models from the GPU* | orchestrator | | | |
| 5 | `lipsync` | producer `--network none` | `audio/<id>.wav` of `aroll` scenes | `lipsync/<id>.json` | |
| 6 | `aroll` | blender | `assets/character_rig.blend`, `lipsync/`, `timing.json` | `aroll/<id>/frame_*.png` → `aroll/<id>.mp4` | |
| 7 | `assemble` | producer `--network none` | All clips + audio | `segments/<id>.mp4`, `out/final.mp4`, `out/final.srt` | |

**The order inside group A (steps 1, 3, 4) is arranged to minimise model switches:** run all scenes through one role, then move to the next role, never interleaving per scene.
- Step 3 (`tts`) runs for **all scenes first**, because `timing.json` must be complete before Manim code is generated.
- Step 4 generates code for all scenes with the LLM, then renders (Manim rendering does not use LocalAI).
- Between group A and group B, the orchestrator calls `POST /backend/shutdown` for each loaded model to free GTT (verified: 16.4 GiB → 0.5 GiB). This avoids stopping the whole LocalAI container.

### 6.2. `config.env`

```bash
OBSIDIAN_VAULT=<absolute-path-to-vault>   # mounted read-only at /vault
LOCALAI_URL=http://localai:8080
ROLE_LLM=planner         # model name in LocalAI (§7.3): ONE model for both script and code
DEFAULT_LANGUAGE=vi      # used when script.json has no `language`; the TTS role is `tts-<language>` (§7.4)
ROLE_STT=whisper-1       # only used in Phase 4
VIDEO_WIDTH=1920
VIDEO_HEIGHT=1080
VIDEO_FPS=30
SCENE_TAIL_PAD=0.3       # extra seconds of silence appended to each scene
BROLL_MAX_ATTEMPTS=3
```

The orchestrator only uses the **role names** from this file. Changing the model only requires changing the YAML in `models/`, not the code.

### 6.3. `script.json` (a human may edit it)

```json
{
  "slug": "banh-rang-truyen-dong",
  "language": "vi",
  "title": "Tỉ số truyền của bánh răng",
  "source_note": "Cơ khí/Bánh răng.md",
  "approved": false,
  "scenes": [
    {
      "id": "s01",
      "type": "aroll",
      "narration": "Vì sao chiếc xe đạp leo dốc dễ hơn khi về số nhỏ?"
    },
    {
      "id": "s02",
      "type": "broll",
      "narration": "Khi bánh răng 24 răng quay một vòng, bánh răng 12 răng ăn khớp với nó phải quay hai vòng.",
      "visual": "Hai bánh răng có răng rõ ràng, 24 và 12 răng, ăn khớp ngang nhau. Bánh lớn quay 1 vòng theo chiều kim đồng hồ, bánh nhỏ quay 2 vòng ngược chiều. Hiện chữ 'Tỉ số truyền 2 : 1'."
    }
  ]
}
```

(Gloss: title "Gear ratio"; s01 narration "Why is climbing a hill on a bicycle easier in a low gear?"; s02 narration "When the 24-tooth gear makes one turn, the 12-tooth gear meshed with it must make two turns."; s02 visual "Two gears with clearly visible teeth, 24 and 12 teeth, meshing horizontally. The big gear turns once clockwise, the small gear twice counter-clockwise. Show the text 'Gear ratio 2 : 1'.")

Rules:
- `language` is the language of the narration, subtitles and on-screen text; it selects the TTS role `tts-<language>` and the subtitle language tag. Falls back to `DEFAULT_LANGUAGE` in `config.env`.
- `id` is unique, of the form `sNN`, and determines scene order.
- `type` accepts only `aroll` or `broll`. A `broll` scene must have `visual`.
- `narration` is the sentence that is read verbatim (in `language`) and also used as the subtitle.
- `visual` is an instruction for the LLM and may be written in any language, but any text it asks to display on screen must be in the video language.

### 6.4. `timing.json` (generated)

```json
{ "s01": { "audio": "audio/s01.wav", "audio_sec": 3.84, "scene_sec": 4.14 } }
```

`scene_sec = audio_sec + SCENE_TAIL_PAD`. This is the **reference** duration every visual clip of the scene must match.

## 7. LOCALAI: INFERENCE SERVICE AND MODEL ORCHESTRATION

### 7.1. Role and principles

LocalAI serves several models through **one endpoint** `http://localai:8080`; the client selects the model with the `model` field of each request. The pipeline uses three roles:

| Role | Job | API | Models |
| :--- | :--- | :--- | :-: |
| `llm` | Generate the script **and** generate/repair Manim code | `POST /v1/chat/completions` | **1** |
| `tts-<lang>` (one per language, e.g. `tts-vi`, `tts-en`) | Read the narration in the video language | `POST /v1/audio/speech` | 1 |
| `stt` | Subtitle timing alignment (Phase 4) | `POST /v1/audio/transcriptions` | 1 |

**Use one LLM for both script and code**, differing only in system prompt and per-request parameters (lower temperature for code). Do not split into separate "script" and "code" models, because:
- Switching models costs load time (~9 s measured with a 4B model, much longer with a 30B model) and extra GPU memory.
- Two YAML files pointing at the same model file may be loaded by LocalAI as two separate processes, doubling memory. This behaviour was not verified, so avoid it.

### 7.2. Containers — `quadlet/producer.network` and `quadlet/localai.container`

`producer.network`:

```ini
[Network]
NetworkName=producer
```

`localai.container`:

```ini
[Unit]
Description=LocalAI for local-producer

[Container]
ContainerName=localai
# Pin by digest; command to get the digest: podman image inspect <image> --format '{{.Digest}}'
# Digest in use on 2026-10-06 (LocalAI v4.11.0):
Image=docker.io/localai/localai@sha256:e9607e90c20278b5b962c47ea7f8a770caaded3c74c1d8c69fbe784fc42fe82a
Network=producer.network
PublishPort=127.0.0.1:8080:8080
AddDevice=/dev/kfd
AddDevice=/dev/dri
GroupAdd=keep-groups
# Value verified to work on gfx1103 (Radeon 780M)
Environment=HSA_OVERRIDE_GFX_VERSION=11.0.2
Environment=THREADS=8
# At most 2 models loaded at once (1 LLM + 1 TTS); the least-recently-used one is evicted when space is needed
Environment=LOCALAI_MAX_ACTIVE_BACKENDS=2
# Automatically free models idle for more than 10 minutes
Environment=LOCALAI_WATCHDOG_IDLE=true
Environment=LOCALAI_WATCHDOG_IDLE_TIMEOUT=10m
Volume=%h/work/ai-agents/local-producer/models:/models
Volume=localai-backends:/backends
Volume=localai-data:/data
Volume=localai-config:/configuration

[Service]
Restart=on-failure
TimeoutStartSec=900
# No [Install]: does not start at login; bin/produce starts/stops it as needed.
```

The memory-control environment variables (`LOCALAI_MAX_ACTIVE_BACKENDS`, `LOCALAI_WATCHDOG_IDLE*`) appear in the documentation and in the image's `local-ai run --help`; passing them through Quadlet had not been tried when this was written.

Operations:

```bash
mkdir -p ~/.config/containers/systemd && cp quadlet/* ~/.config/containers/systemd/
systemctl --user daemon-reload
systemctl --user start localai        # start
systemctl --user stop localai         # stop
journalctl --user -u localai -f       # follow logs
```

**Migrating data from the old container.** The existing `local-ai` container (created with `podman run`) had already downloaded the backends (~11 GB) and two trial models. To avoid downloading again, copy from the anonymous volumes to where Quadlet uses them:
- the old container's `/models` → `local-producer/models/`
- the old container's `/backends` → volume `localai-backends`

Find the paths with `podman inspect local-ai --format '{{json .Mounts}}'` and copy with `cp -a`. Only after Quadlet runs correctly, `podman rm local-ai` and remove the anonymous volumes with `podman volume rm <id>`. Do not use `podman volume prune`, which deletes every volume without a container.

**Internet is needed to install, not to operate.** Installing models and backends (`POST /models/apply`) downloads from the network; once installed, LocalAI runs offline. GPU backends are large (the `crispasr` backend is ~2.8 GiB to download, ~6.4 GiB unpacked), so installation is done once, in Phase 0–1.

### 7.3. LLM model — `models/planner.yaml`

The defaults taken from the gallery are **not usable as-is** (see §3.2). The YAML of the `llm` role must set things explicitly:

```yaml
name: planner                 # matches ROLE_LLM in config.env
backend: llama-cpp
context_size: 16384           # do NOT leave the default 262144
parallel: 1                   # or an equivalent setting (see note below); gallery default is 4 slots
gpu_layers: 99
mmap: true
parameters:
  model: <CHOSEN_GGUF_FILE>
  temperature: 0.4
options:
  - use_jinja:true
```

Notes:
- The exact key that limits the number of parallel slots (`parallel`) depends on the LocalAI version. The startup log prints a line `effective runtime tuning … parallel="4"`; after editing the YAML, check that this line shows `parallel="1"` and `context=16384`. This is a mandatory acceptance check in Phase 0.
- **Disable thinking mode.** For Qwen3.x models, send `"chat_template_kwargs": {"enable_thinking": false}` in every request and set `max_tokens` high enough (script ≥ 2000, Manim code ≥ 3000). Always read `choices[0].message.content`; if `content` is empty treat it as an error and retry, never read from `reasoning`. (Later finding: with LocalAI v4.11.0 the request-level parameter is ignored; use `reasoning: {disable: true}` in the model YAML instead — see `CHANGELOG.md`.)
- **Structured output:** use `response_format: {"type": "json_object"}` and still re-validate with the schema (§8.1).

**Choosing the model (to be decided in Phase 0):**
- Preferred: an **MoE model, ~30–35B total, ~3B active parameters**, Q4 quantisation (the LocalAI gallery has entries such as `qwen3.8-35b-a3b-distill-q4` and `nemotron-3.5-lightning-30b-a3b-q4`). On an iGPU generation speed is limited by RAM bandwidth, so a model that activates only ~3B parameters per token is much faster than a dense model of the same size. Cross-check: a dense 4B model measured ~20 tokens/s, so an MoE with ~3B active parameters is expected to be in the same range, but this was **not measured** at the time.
- Fallback: a dense 9–14B model in Q4.
- Do not use dense 27–32B models: expected to give only a few tokens/s, too slow for a code-repair loop.
- Phase 0 compares on three criteria: rate of valid JSON, rate of Manim code that runs on the first try, tokens/s.

### 7.4. Voice — `models/tts-<lang>.yaml`

**Multi-language.** The video language is set per request in `script.json` (`language`, an ISO 639-1 code such as `vi` or `en`). The orchestrator picks the LocalAI model named `tts-<language>`; to support a new language, install a voice for it and give its YAML that name, no code change. If no `tts-<language>` model exists the `tts` step fails with a clear error. Only Vietnamese has been tried; the rest of this section uses Vietnamese as the worked example.

Installation that worked (LocalAI gallery, backend `crispasr`):

```bash
curl -s -X POST localhost:8080/models/apply -H 'Content-Type: application/json' \
     -d '{"id":"localai@piper-vi_VN-vais1000-medium-crispasr"}'
```

The YAML generated by LocalAI on install (use as a template; name it `tts-<lang>`, here `tts-vi`):

```yaml
name: tts-vi
backend: crispasr
known_usecases:
  - tts
options:
  - backend:piper
parameters:
  model: piper-vi_VN-vais1000-medium-f16.gguf
```

Call: `POST {LOCALAI_URL}/v1/audio/speech` with `{"model": "tts-<lang>", "input": "<narration>"}`. The orchestrator always converts the result to **16-bit PCM WAV, 48 kHz, mono** with FFmpeg (the native output is 22.05 kHz); this format is shared by Rhubarb and the assembly step.

**Three candidate voices to compare by ear in Phase 1** (not yet listened to, quality not assessed):

| Candidate | Gallery id | Notes |
| :--- | :--- | :--- |
| piper `vi_VN-vais1000-medium` | `piper-vi_VN-vais1000-medium-crispasr` | Already runs; lightest. A `25hours_single-low` variant also exists |
| Supertonic-3 | `supertonic-3` | Supports 31 languages including Vietnamese (per the model docs); ONNX, 44.1 kHz, 10 built-in voices |
| VoxCPM2 | `voxcpm2` | 2B model, 30 languages including Vietnamese (per the model docs); voice design/cloning, 48 kHz; heavier than the other two |

Kokoro is **not** usable for Vietnamese because it does not support it (it may be worth evaluating for other languages; not verified). VieNeu-TTS is not in the gallery, so it is only the last resort (separate `tts-vieneu` container).

### 7.5. LocalAI API used by the orchestrator

| Task | Call |
| :--- | :--- |
| Readiness check | `GET /readyz` |
| List installed models | `GET /v1/models` |
| Generate text | `POST /v1/chat/completions` |
| Generate speech | `POST /v1/audio/speech` |

| Install model / backend (manual, once) | `POST /models/apply`, `POST /backends/apply`; progress at `GET /models/jobs` |

### 7.6. Model orchestration policy

There are four layers, from active to automatic:

1. **Active orchestrator (the main layer):** at the start of each step group call `GET /readyz`; at the end of group A call `/backend/shutdown` for `planner` and `tts-<lang>`, then check that GTT usage has dropped before letting Blender run. If GTT stays abnormally high, stop and report an error; do not render on.
2. **`LOCALAI_MAX_ACTIVE_BACKENDS=2`:** prevents loading more than two models at once; the most recently used model is kept, the oldest is evicted when space is needed.
3. **`LOCALAI_WATCHDOG_IDLE`:** a model idle for more than 10 minutes is freed automatically, in case the orchestrator was interrupted midway.
4. **`concurrency_groups` (optional, in each model's YAML):** only needed if there are later several heavy models that must not be loaded together. Not needed with the current setup (one LLM + one light TTS).

Two additional requirements:
- GPU memory must **not** be heavily occupied by LocalAI and Blender at the same time: total GTT is 30 GiB, so Blender always runs after the LLM has been freed.
- If a request to LocalAI fails because a model is being reloaded, the orchestrator retries up to 3 times with increasing delay.

### 8.2. How `bin/produce` runs jobs

Parameters common to every job:

```bash
COMMON=(--rm --userns=keep-id            # generated files belong to the current user, not root
        -v "$ROOT/src:/app:ro"
        -v "$PROJ:/work")
```

| Job | Command (abridged) |
| :--- | :--- |
| Call LLM/TTS | `podman run "${COMMON[@]}" --network producer -v "$OBSIDIAN_VAULT:/vault:ro" --env-file config.env localhost/producer plan <note>` |
| Render generated code | `podman run "${COMMON[@]}" --network none --cpus 6 localhost/producer broll-render s02` |
| Blender | see §8.4 |

Host command line:

```bash
bin/produce doctor                                  # check the environment (§8.4, §10.5)
bin/produce new <slug> "<path/to/note.md>"          # step 1, then stops and waits for review
bin/produce run <slug>                              # steps 3–7, refuses if not approved
bin/produce step <step-name> <slug> [scene-id]      # re-run one step / one scene
```

### 8.3. `plan`, `tts`, `broll` (Manim), `lipsync`

**`plan` — script generation**
1. Read the note from `/vault`: strip frontmatter, turn `[[links]]` into plain text, keep LaTeX formulas.
2. Call the `llm` role (set up in §7.3). The prompt requires: use only information present in the note, add no outside figures; narration in the video language (`language` in the script), 1–3 sentences per scene; alternate `aroll` (lead-in) and `broll` (mechanism illustration); `visual` descriptions must be concrete and countable (number of teeth, rotation direction, displayed values).
3. Validate the JSON with a pydantic schema (§6.3). If invalid, send the error back to the LLM, at most 3 times.
4. Write `script.json` with `"approved": false`.

**Review:** a human compares `narration` with the source note, edits `script.json` directly, then sets `"approved": true`.

**`tts` — voice-over.** For each scene: call the `tts-<language>` role → normalise to 48 kHz mono s16 WAV → measure duration with `ffprobe` → write `timing.json`. If a technical term is mispronounced, fix it by rewriting `narration` the way it should be read, e.g. in Vietnamese "Hz" is written out as "héc".

**`broll` — Manim.** Each `broll` scene runs a loop of at most `BROLL_MAX_ATTEMPTS` attempts:

```
broll-gen    (producer network)  : the LLM generates broll/<id>.py
                                   (later attempts: include the old code + last 60 lines of broll/<id>.log to repair it)
broll-render (--network none)    : static check → manim render → write broll/<id>.log
   ├─ success and valid duration → done
   └─ failure → repeat
Out of attempts → mark the scene FAILED; a human fixes `visual` or edits broll/<id>.py by hand and re-runs the step.
```

Constraints put into the prompt:
- Manim Community (the exact version in the image), one class named `Scene_<id>`, only `from manim import *` and `numpy`.
- Total animation time ≈ `scene_sec` (from `timing.json`). End with `self.wait()` to fill any remainder.
- On-screen text uses `Text(...)` with a Noto font that covers the video's script (`Noto Sans` covers Latin including Vietnamese; for other scripts such as CJK add the matching Noto font package to the image). Text shown on screen must be in the video language. Use `MathTex` only for formulas, because default LaTeX does not handle non-ASCII diacritics or other scripts.
- Objects must match the description; e.g. gears must have teeth, because a plain circle rotating looks stationary.

Static check before rendering: reject code that has an `import` other than `manim`/`numpy`/`math`, or calls `open`, `exec`, `eval`, `__import__`. This is only a secondary layer; the primary isolation is the `--network none` container that mounts only `/work`.

```bash
manim render --resolution 1920,1080 --frame_rate 30 --disable_caching \
      --media_dir /work/broll/media -o s02 /work/broll/s02.py Scene_s02
```

Valid when the clip duration is within `scene_sec ± 20%`; small deviations are compensated in the `assemble` step.

**`lipsync` — Rhubarb** (`producer` container, `--network none`):

```bash
rhubarb -r phonetic -f json --extendedShapes GHX -o /work/lipsync/s01.json /work/audio/s01.wav
```

`-r phonetic` is mandatory: the default recogniser is English-only, while the phonetic one is language-independent. The result contains 9 mouth shapes: `A B C D E F` (basic), `G H X` (extended, `X` is rest).

### 8.4. Blender — A-roll

Blender has **two usage modes** with different roles:

| | Rig building (manual) | Automated rendering (pipeline) |
| :--- | :--- | :--- |
| Purpose | Create/edit `character_rig.blend`: model, mouth shape keys, lighting, camera | Run `aroll_render.py` for each scene |
| Where it runs | **On the real machine**, unpack the official tarball into `~/opt/blender-<version>/` (no apt/snap; deleting the folder uninstalls it) | **`blender` container**, `-b` (headless) |
| Needs a display | Yes | **No** (verified) |
| Version | Must match the container | Must match the real machine |

Why the rig is built on the real machine: the graphical Blender UI does run in a container but is awkward (file dialogs only see mounted directories, Preferences/addons are lost after `--rm`, font/IME/scale problems may occur because it has to go through Xwayland). Automated rendering in the container has the same performance as running directly: the container shares the kernel and GPU, with no virtualisation layer.

**Version:** pin **Blender 5.2.2 LTS** (supported until 07/2028) for both the real machine and the container. Fallback: 4.5.14 LTS (supported until 07/2027). Both were built and test-rendered successfully in the container. `aroll_render.py` must run on both versions (see the API notes below).

**Image — `images/blender/Containerfile`** (built and run with 4.5.14 and 5.2.2):

```dockerfile
# Use the same Ubuntu release as the host to get the same Mesa (host: Mesa 26.0.8)
FROM docker.io/library/ubuntu:26.04

RUN apt-get update && apt-get install -y --no-install-recommends \
        ca-certificates curl xz-utils \
        libgl1 libegl1 libgl1-mesa-dri libvulkan1 mesa-vulkan-drivers vulkan-tools \
        libx11-6 libxi6 libxxf86vm1 libxfixes3 libxrender1 libxkbcommon0 \
        libsm6 libice6 libwayland-client0 libwayland-egl1 libdecor-0-0 libxext6 \
        libxkbcommon-x11-0 libxcb1 libsndfile1 \
    && rm -rf /var/lib/apt/lists/*

ARG BLENDER_VERSION
RUN curl -fsSL "https://download.blender.org/release/Blender${BLENDER_VERSION%.*}/blender-${BLENDER_VERSION}-linux-x64.tar.xz" \
      | tar -xJ -C /opt \
    && ln -s /opt/blender-${BLENDER_VERSION}-linux-x64/blender /usr/local/bin/blender

ENV HOME=/tmp
WORKDIR /work
```

```bash
podman build --build-arg BLENDER_VERSION=5.2.2 -t localhost/producer-blender images/blender
```

Use the same Ubuntu release as the host (26.04) because a newer Mesa is usually better for RDNA3; both are currently Mesa 26.0.8.

**Render command** (works in this form; no X/Wayland, no display socket mount, no `xvfb`):

```bash
podman run --rm --userns=keep-id --network none \
  --device /dev/dri --group-add keep-groups \
  -v "$ROOT/assets:/assets:ro" -v "$ROOT/src:/app:ro" -v "$PROJ:/work" \
  localhost/producer-blender \
  blender -b /assets/character_rig.blend --gpu-backend vulkan \
          -P /app/blender/aroll_render.py -- --scene s01
```

- `--gpu-backend vulkan` must be given explicitly. At run time the container sees **two** Vulkan devices: `AMD Radeon 780M (RADV)` and `llvmpipe` (CPU rendering). Blender picked RADV on its own, but this must be checked automatically: `bin/produce doctor` renders a test frame with `--debug-gpu` and **fails if the line `Using vendor … device […]` does not contain `RADV`** (see §10.5).
- The `aroll` step runs even without a desktop session.
- Fallback if Vulkan has problems with the real rig: `--gpu-backend opengl` (rendered fine in `-b`), or Cycles on CPU (much slower).

**Requirements for `assets/character_rig.blend`** (a hand-made asset or one from a suitably licensed source; an LLM cannot generate it):
- Mouth shape keys named `mouth_A` … `mouth_H`, `mouth_X`.
- A looping idle action (blinking, slight head sway) so the avatar does not stand frozen.
- Camera and lighting set up; EEVEE; 1920×1080 @ 30 fps.
- Saved with **exactly the pinned Blender version** above (a file saved with a newer version may not open in an older one).

**`src/blender/aroll_render.py`** (fixed code, not LLM-generated):
1. Read `lipsync/<id>.json` and `timing.json`.
2. Set `frame_end = ceil(scene_sec × fps)`.
3. For each `mouthCue`: keyframe the matching shape key = 1 and all other shape keys = 0, with CONSTANT interpolation.
4. Pick the engine by version: `BLENDER_EEVEE_NEXT` if `bpy.app.version < (5, 0, 0)`, otherwise `BLENDER_EEVEE`.
5. Write a **PNG sequence** to `aroll/<id>/frame_####.png` (`file_format = 'PNG'`). Do **not** write video directly from Blender: in 5.2 `file_format = 'FFMPEG'` is no longer valid as in 4.x, so encoding is a separate step so that one script runs on both versions.
6. Encode with FFmpeg (in the `producer` container): `ffmpeg -framerate 30 -i aroll/<id>/frame_%04d.png -c:v libx264 -crf 18 -pix_fmt yuv420p aroll/<id>.mp4`.

A side benefit of the PNG sequence: if rendering is interrupted midway, only the missing frames need to be rendered.

### 8.5. `assemble` — FFmpeg

**Step 1: normalise each scene** into `segments/<id>.mp4`. Every segment has the same codec, resolution, fps, pix_fmt and audio format, so the later concatenation may copy streams.

```bash
D=4.14   # scene_sec of the scene
ffmpeg -y -i broll/s02.mp4 -i audio/s02.wav -filter_complex "
  [0:v]scale=1920:1080:force_original_aspect_ratio=decrease,pad=1920:1080:(ow-iw)/2:(oh-ih)/2,
       fps=30,format=yuv420p,tpad=stop_mode=clone:stop_duration=60,trim=duration=$D,setpts=PTS-STARTPTS[v];
  [1:a]aresample=48000,apad,atrim=duration=$D,asetpts=PTS-STARTPTS[a]" \
  -map "[v]" -map "[a]" \
  -c:v libx264 -preset medium -crf 18 -c:a aac -b:a 192k -ar 48000 -ac 2 \
  segments/s02.mp4
```

A clip shorter than `D` holds its last frame (`tpad`); a longer clip is cut (`trim`); audio is padded with silence up to `D`.

**Step 2: concatenate** (no re-encode, safe because all segments are uniform):

```bash
ffmpeg -y -f concat -safe 0 -i segments.txt -c copy out/concat.mp4
```

If a "click" is heard at the joins (AAC priming), switch to the `concat` filter and re-encode.

**Step 3: subtitles.** Generate `out/final.srt` from `narration` and `timing.json`: split sentences, divide the scene duration in proportion to character count, at most 42 characters per line and at most 2 lines. (Phase 4: re-align with the `stt` role.)

**Step 4: loudness normalisation and packaging:**

```bash
ffmpeg -y -i out/concat.mp4 -i out/final.srt -map 0:v -map 0:a -map 1 \
  -c:v copy -af loudnorm=I=-14:TP=-1.5:LRA=11 -c:a aac -b:a 192k -ar 48000 \
  -c:s mov_text -metadata:s:s:0 language=<iso639-2 code of script.language, e.g. vie> out/final.mp4
```

Note: `-c:v copy` combined with `-af` is valid (the filter applies only to audio). Subtitles are packaged as soft subtitles; `final.srt` is also kept separately for uploading to video platforms.

## 9. RESOURCES AND PERFORMANCE

### 9.1. Memory budget

GTT is 30 GiB. Real measurements existed only for the 4B model at the time of writing (see §3.2); the other rows are estimates that had to be re-measured in Phase 0.

| Group | Component | Memory | Source |
| :--- | :--- | :--- | :--- |
| A | 4B Q8 LLM, context 262144, 4 slots (default configuration, **not used**) | 16.4 GiB GTT | Measured |
| A | LLM with `context_size: 16384`, 1 slot | To be measured | Phase 0 |
| A | MoE ~30–35B Q4 LLM (weights + KV cache) | ~20–24 GiB | Estimate |
| A | piper TTS | Small (< 1 GiB) | Estimate |
| A | Manim render | 1–3 GiB RAM | Estimate |
| B | Blender EEVEE (real rig) | 2–8 GiB | Estimate |
| B | FFmpeg | < 1 GiB | Estimate |

The two groups do not overlap because the LLM is freed before Blender runs.

### 9.2. GPU memory

- **Keep the BIOS VRAM carve-out low (currently 1 GiB).** llama.cpp and Mesa (Blender/Vulkan) can both allocate from GTT; the log showed the 4B model occupying 16 GiB of GTT while VRAM was only ~0.8 GiB. Raising the carve-out only reduces system RAM without increasing usable GPU memory.
- If a model larger than the 30 GiB GTT limit is needed later, raise the GTT limit with the kernel parameter `ttm.pages_limit`. Do not do this while the current model already fits.
- Because Vulkan does not spill GPU memory into RAM the way OpenGL does, a Blender scene that is too large may report out-of-memory instead of running slowly. Check with the real rig in Phase 3.

### 9.3. Temperature and power

- Do not use `ryzenadj`: it must be installed on the host and needs SMU access, which is usually blocked when Secure Boot is on.
- Use the built-in `powerprofilesctl`. The machine was on `power-saver`; `bin/produce` sets `balanced` while running heavy jobs and restores the previous mode when done.
- Limit CPU for render jobs with `--cpus 6` so the machine stays usable during rendering.
- Measure the actual temperature (`/sys/class/hwmon/*/temp*_input`) in Phase 0 and record it in this document. The document gives no temperature figure before it has been measured.

### 9.4. Processing time

Only commit to the figures measured in §3.2. Phases 0–3 additionally measure: tokens/s of the chosen LLM (prompt and generation), TTS seconds per audio second, Manim render seconds per video second, EEVEE render seconds per frame with the real rig.

## 13. NOTES ON CLAUDE CODE

Version 1.0 proposed pointing Claude Code at LocalAI (`ANTHROPIC_BASE_URL`) to act as the orchestrator. This option was **rejected** because:
- The pipeline must run reliably and repeatably. An orchestrator written as code (§5, §7.6) provides that; an agent that decides the step order by itself does not.
- Local models of this size are poor at tool calling. Every Claude Code turn sends a very long system prompt which the iGPU has to reprocess from scratch, making each turn slow.
- It depends on LocalAI being compatible with the Anthropic Messages API, which was not verified.

Claude Code is still useful as a **development tool** (writing `src/`, Containerfiles, debugging), used with the real Claude over the internet. That is separate from the operating pipeline, which would still run fully offline.
